## چرا این پروژه؟

پنل پاسارگارد عددی به نام «حجم مصرفی هر ادمین» دارد. آن عدد **مصرف واقعی مشتری‌ها** است،
نه چیزی که ادمین **فروخته**. این دو با هم فرق دارند و دقیقاً همان‌جا ضرر می‌کنی:

| کاری که ادمین می‌کند | پنل نشان می‌دهد | این بات حساب می‌کند |
|---|---:|---:|
| اکانت ۱۰۰ گیگ می‌سازد، مشتری مصرف نمی‌کند | `0` | **100 GB** |
| اکانت ۳۰ گیگ می‌سازد، چند ساعت بعد حذفش می‌کند | `0` (کاملاً ناپدید) | **30 GB** |
| اکانت ۱۰ گیگ، تا ۹٫۹ گیگ مصرف، بعد حذف | `9.9 GB` | **10 GB** |
| اکانت ۴۰ گیگ، ۳۹ گیگ مصرف، بعد **ریست** | `0` (بعد از ریست) | **80 GB** (۴۰ + ۴۰) |
| حجم اکانت موجود را از ۱۰۰ به ۱۶۰ زیاد می‌کند | تغییری نمی‌کند | **+60 GB** |
| همه‌ی یوزرهایش را دسته‌جمعی ریست می‌کند | لاگی باقی نمی‌ماند | **شناسایی می‌شود** ✅ |
| ۲۰ اکانت می‌سازد و به تو می‌گوید ۱۷ تا بوده | — | **اسم هر ۲۰ تا** |

> **هدف:** هیچ فروشی گم نشود — حتی اگر ادمین اکانت را قبل از پایان روز حذف کند.

## نصب (۵ دقیقه)

### ۱) توکن بات

به [@BotFather](https://t.me/BotFather) پیام بده → `/newbot` → یک اسم و یوزرنیم بده
(یوزرنیم باید به `bot` ختم شود). توکن را کپی کن.

### ۲) آیدی چت

- **خودت:** به [@userinfobot](https://t.me/userinfobot) پیام بده.
- **گروه:** بات را در گروه ادمین کن؛ آیدی گروه با `-100` شروع می‌شود.

### ۳) نصب

```bash
cd /opt
git clone https://github.com/lastdejavu/pg-accountant.git
cd pg-accountant
sudo bash install.sh --token "توکن_اینجا" --chats "123456789,-1001234567890"
```

بدون آرگومان هم اجرا کنی، تعاملی می‌پرسد. اسکریپت خودش:

- نوع دیتابیس را از `/opt/pasarguard/.env` تشخیص می‌دهد
- درایور درست را نصب می‌کند (`psycopg2-binary` / `pymysql` / sqlite) و **import شدنش را تأیید می‌کند**
- اتصال به دیتابیس را تست می‌کند
- سرویس `systemd` می‌سازد و فعال می‌کند

### ۴) قبل از شروع، دیتابیس را اعتبارسنجی کن

```bash
sudo /opt/pg-accountant/venv/bin/python /opt/pg-accountant/bot.py \
  -c /opt/pg-accountant/config.ini checkdb
```

خروجی سالم:

### اگر ادمین‌هایت زیادند

گزارش به‌صورت **یک پیام خلاصه + یک پیام جدا برای هر ادمین** می‌رود، پس با
ده‌ها ادمین هم هیچ پیامی شلوغ نمی‌شود و می‌توانی گزارش هر ادمین را جدا برایش
فوروارد کنی:

```
📅 2026-09-22
──────────────
👥 ادمین‌های فعال: ۳۰   |   📦 مجموع: 36.62 TB
🆕 اکانت جدید: ۷۵۰

۱. admin_00 — 1.22 TB  (۲۵ اکانت)
۲. admin_01 — 1.22 TB  (۲۵ اکانت)
…
──────────────
💰 جمع بیل‌شده: 36.62 TB
```

```
📊 گزارش حجم ادمین‌ها          ← پیام ۲: فقط ادمین اول
📅 2026-09-22
──────────────
۱ از ۳۰
👤 admin_00
   📦 1.22 TB   |   🆕 ۲۵ اکانت   |   🔁 ۰ ریست
   ├ a00_user_00 — 50 GB
   ├ a00_user_01 — 50 GB
   └ … و ۲۳ مورد دیگر (1.13 TB)
```

اگر تعداد ادمین‌ها از `max_admin_messages` بیشتر شود، فقط آن‌ها که حجم
بیشتری دارند پیام جزئیات می‌گیرند و بقیه در همان خلاصه می‌مانند؛ خلاصه هم
یادآوری می‌کند که با `/admin نام‌ادمین` می‌توانی جزئیات هر کدام را بگیری.

با `report_per_admin = false` برمی‌گردد به حالت فشرده (ادمین‌ها تا سقف
اندازه در یک پیام).

### ⚠️ درباره‌ی اولین اجرا

در اولین اجرا، بات **اکانت‌های موجود در پنل را هم ثبت می‌کند** تا آمار از روز اول
کامل باشد. اگر پنلت پر از اکانت قدیمی است و نمی‌خواهی گذشته در آمار بیاید،
**قبل از اولین اجرا** بگذار:

```ini
backfill_on_first_run = false
```

## خط فرمان

```bash
BIN=/opt/pg-accountant/venv/bin/python
BOT=/opt/pg-accountant/bot.py
CFG=/opt/pg-accountant/config.ini

sudo $BIN $BOT -c $CFG health      # تست اتصال
sudo $BIN $BOT -c $CFG checkdb     # اعتبارسنجی کامل اسکیمای پنل
sudo $BIN $BOT -c $CFG scan        # یک اسکن فوری
sudo $BIN $BOT -c $CFG status      # وضعیت
sudo $BIN $BOT -c $CFG report      # گزارش دیروز در ترمینال
sudo $BIN $BOT -c $CFG report 2026-09-20 --send   # همان، ولی ارسال به تلگرام
sudo $BIN $BOT -c $CFG daily       # گزارش دیروز + ارسال (مناسب cron)
sudo $BIN $BOT -c $CFG run         # اجرای دائمی (همان کاری که systemd می‌کند)
```

اگر ترجیح می‌دهی گزارش را `cron` بفرستد:

```cron
5 0 * * * /opt/pg-accountant/venv/bin/python /opt/pg-accountant/bot.py -c /opt/pg-accountant/config.ini daily >> /var/log/pg-accountant.log 2>&1
```

## چطور کار می‌کند؟

هر `scan_interval` ثانیه، بات جدول `users` پنل را می‌خواند و با دفترکل خودش
(`ledger.db`) مقایسه می‌کند:

| تغییر مشاهده‌شده | رویداد | چه چیزی بیل می‌شود |
|---|---|---|
| کاربر جدید دیده شد | `provision` | `data_limit` فعلی |
| `used_traffic` افت کرده | `reset` | `data_limit` فعلی (فروش مجدد) |
| `data_limit` زیاد شده | `topup` | مابه‌التفاوت |
| حجم و مصرف **هم‌زمان** عوض شده | `renewal` | فقط `data_limit` جدید — **یک بار** |
| `data_limit` کم شده | `limit_cut` | هیچ (فقط ثبت هشدار) |
| کاربر ناپدید شده | `deleted` | هیچ (قبلاً در `provision` حساب شده) |

`data_limit` پنل به **بایت** است. بات همان را بیل می‌کند و در گزارش به گیگ/ترابایت
با مبنای ۱۰۲۴ نشان می‌دهد — دقیقاً مثل خود پنل.

### چرا ریست دسته‌جمعی را می‌گیرد؟

تابع `bulk.py` در پنل، ریست دسته‌جمعی را با یک `UPDATE` ساده انجام می‌دهد،
**هیچ ردیفی در `user_usage_logs` نمی‌نویسد** و ردیف‌های قبلی را هم پاک می‌کند:

```python
await db.execute(update(User).where(User.id.in_(user_ids)).values(used_traffic=0, ...))
await db.execute(delete(UserUsageResetLogs).where(UserUsageResetLogs.user_id.in_(user_ids)))
```

پس اتکا به آن جدول فایده‌ای ندارد. بات ریست را از **افت `used_traffic` بین دو
اسکن** تشخیص می‌دهد، که با هر روش ریستی کار می‌کند.

### چرا `renewal` لازم است؟

وقتی پنل `next_plan` را اعمال می‌کند، هم `data_limit` عوض می‌شود و هم
`used_traffic` صفر. اگر هر دو جداگانه حساب شوند، تمدید یک پلن ۴۰ گیگی به
۱۰۰ گیگ این‌طور درمی‌آید:

```
تغییر حجم:  ۱۰۰ − ۴۰ = +۶۰
ریست:                  +۱۰۰
                       ─────
جمع:                   ۱۶۰   ❌ (درست: ۱۰۰)
```

بات این حالت را به‌عنوان یک رویداد `renewal` ثبت می‌کند و فقط `۱۰۰` حساب می‌شود.

## مقایسه با روش Trigger

یک راه دیگر هم برای همین کار هست: گذاشتن `TRIGGER` روی جدول `users`
(مثل [`pasarguard-admin-report`](https://github.com/lastdejavu/pasarguard-admin-report)).
هر دو روش درست‌اند؛ فرقشان در بده‌بستان است:

| | Trigger روی پنل | این پروژه (polling) |
|---|---|---|
| دیتابیس پشتیبانی‌شده | فقط MySQL/MariaDB | PostgreSQL · TimescaleDB · MySQL · MariaDB · SQLite |
| دست به دیتابیس پنل | جدول + trigger می‌سازد | **هیچ** — فقط `SELECT` |
| پنجره‌ی از دست رفتن | صفر | `scan_interval` (پیش‌فرض ۶۰ ثانیه) |
| دوام بعد از آپدیت پنل | ممکن است migration آن را بپراند | مستقل از اسکیمای داخلی پنل |
| گزارش‌های تعاملی | ندارد | `/report` `/week` `/admin` `/user` |
| تست خودکار | ندارد | ۱۴۰ بررسی + CI |

**اگر پنلت MySQL/MariaDB است**، روش Trigger پنجره‌ی از دست رفتن ندارد و انتخاب
بهتری است. **اگر PostgreSQL یا TimescaleDB داری** (که خودِ مستندات پاسارگارد
پیشنهاد می‌کند)، سینتکس `DELIMITER` و `@var :=` در PostgreSQL کار نمی‌کند و این
پروژه تنها گزینه است.

## محدودیت‌ها (صادقانه)

- **پنجره‌ی `scan_interval`:** اگر ادمین اکانتی را در کمتر از ۶۰ ثانیه بسازد و
  حذف کند، ثبت نمی‌شود. با `scan_interval = 15` این پنجره به ۱۵ ثانیه می‌رسد؛
  بار روی دیتابیس ناچیز است (دو `SELECT` ساده).
- **خاموشی بات:** اکانت‌هایی که در فاصله‌ی خاموشی ساخته شده و **هنوز موجودند**
  از روی `users.created_at` بازیابی می‌شوند. اکانتی که در آن فاصله **ساخته و حذف**
  شده باشد قابل بازیابی نیست، چون پنل اثری از آن نگه نمی‌دارد. اگر بات بیش از
  ۵ دقیقه خاموش بوده باشد، هشدار ثبت می‌شود.
- **اکانت نامحدود:** `data_limit = NULL` را نمی‌توان به گیگابایت تبدیل کرد؛ بات
  آن‌ها را می‌شمارد ولی صفر بیل می‌کند و در گزارش `∞` نشان می‌دهد.
- **روی PostgreSQL واقعی تست نشده:** تست‌های خودکار روی SQLite با اسکیمای واقعی
  پنل اجرا می‌شوند و کوئری‌ها برای دیالکت PostgreSQL کامپایل شده‌اند، ولی یک
  سرور PostgreSQL زنده در محیط توسعه در دسترس نبود. قبل از شروع، `checkdb` را
  بزن — دقیقاً همین شکاف را پر می‌کند.

## امنیت

### دیتابیس پنل در سطح دیتابیس قفل می‌شود

بات فقط به این امید که کدش چیزی نمی‌نویسد، read-only نیست — اتصال در **سطح
خودِ دیتابیس** قفل می‌شود:

| دیتابیس | دستور قفل |
|---|---|
| SQLite | `PRAGMA query_only = ON` |
| PostgreSQL / TimescaleDB | `SET default_transaction_read_only = on` |
| MySQL / MariaDB | `SET SESSION TRANSACTION READ ONLY` |

یعنی حتی اگر باگی در بات باشد، `INSERT`/`UPDATE`/`DELETE` از سمت دیتابیس رد
می‌شود. این تنظیمات فقط روی **جلسه‌ی اتصال** اثر دارند و هیچ چیزی روی سرور
تغییر نمی‌دهند — نه نقش جدید، نه `GRANT`، نه تغییر فایل.

`checkdb` این قفل را **واقعاً امتحان می‌کند** (یک نوشتن آزمایشی می‌زند و
مطمئن می‌شود رد شده):

```
-- قفل فقط‌خواندنی --
  نوشتن        : ✅ رد می‌شود — دیتابیس نوشتن را رد کرد (sqlite)
```

اگر قفل کار نکند، `checkdb` با کد خروج `۱` و پیام واضح برمی‌گردد.

### بقیه

- نصب‌کننده **هیچ دسترسی‌ای روی فایل‌های پنل تغییر نمی‌دهد** — حتی `chmod`.
  تنها `chmod` روی `config.ini` خودِ بات است.
- دفترکل در فایل جدا (`ledger.db`) است؛ پاک کردنش به پنل آسیب نمی‌زند.
- `config.ini` با دسترسی `۶۰۰` نوشته می‌شود (فقط روت).
- رمز دیتابیس در `config.ini` ذخیره نمی‌شود؛ هر بار از `.env` پنل خوانده می‌شود.
- اگر `allowed_chat_ids` خالی باشد، هر کسی که بات را پیدا کند می‌تواند آمار
  ادمین‌هایت را ببیند. **حتماً پرش کن.**
- بار بات روی دیتابیس پنل: دو `SELECT` ساده در هر دقیقه.

برای حذف کامل، کافی است `/opt/pg-accountant/` و سرویسش را پاک کنی —
هیچ اثری روی پنل نمی‌ماند.

## رفع اشکال

| مشکل | راه‌حل |
|---|---|
| `ModuleNotFoundError: psycopg2` | `sudo /opt/pg-accountant/venv/bin/pip install psycopg2-binary`<br>اگر نصب نشد: `apt install -y libpq-dev gcc python3-dev` |
| `connection refused` | دیتابیس داخل Docker است؟ مطمئن شو پورت به `127.0.0.1` نگاشت شده |
| گزارش نمی‌آید | `allowed_chat_ids` را چک کن؛ بات را در گروه ادمین کرده‌ای؟ |
| `Permission denied` روی دیتابیس | برای SQLite: `chmod a+r /var/lib/pasarguard/db.sqlite3` |
| آمار با پنل نمی‌خواند | طبیعی است — پنل **مصرف** را نشان می‌دهد، بات **فروش** را. [جدول بالا](#چرا-این-پروژه) را ببین |
| بات بعد از ری‌استارت گزارش خالی می‌فرستد | در نسخه‌ی فعلی رفع شده؛ مطمئن شو `git pull` کرده‌ای |

لاگ‌ها:

```bash
sudo journalctl -u pg-accountant -f
sudo tail -f /var/log/pg-accountant.log
```
